# Predictive Analysis System — Full Plan & Backend Architecture

> Current design of record for the predictive/analysis layer. Builds on
> `ANALYSIS_LAUNCHER_DECISION.md`, `FEATURE_DISCUSSION_CONTEXT.md`, `PLAN_IN_SIMPLE_WORDS.md`.
> Scope locked: **Tiers 1, 2, 3**, relational drill-down + prediction + recommendations, Preview DB
> extended with dates / teacher-batch / contacts.

---

## 0. What the system must do

For any analysis request, the system must: **query the data → have the LLM analyze it → predict/score →
give prioritized recommendations**, and let the user **drill down through relationships** in chat. Today
such a request goes unanswered (the app only does simple retrieval). This plan closes that gap.

---

## 1. THE BACKEND DECISION (the important part)

**Recommended: a thin server-side "Analysis Brain" on the existing `server.mjs`, while the deterministic
SQL stays in the browser (DuckDB-wasm).** "Numbers where the data is; reasoning where the keys are safe."

### The split
- **Browser (as today):** runs DuckDB-wasm over the CSVs, executes the SQL, renders charts. The heavy
  data (65–190 MB) stays on the user's machine — no server memory problem.
- **Server (`server.mjs` + new `/api` routes):** holds the **LLM API keys**, holds the **playbooks +
  catalog**, and runs the **LLM orchestration** (write SQL → interpret → predict → recommend).

### The request round-trip
1. Browser → `POST /api/plan` `{question, mode, filters, history}` → server LLM returns **SQL + which
   playbook** (LLM call 1).
2. Browser **executes that SQL locally** in DuckDB → rows (deterministic numbers).
3. Browser → `POST /api/analyze` `{question, rows, playbook, mode}` → server LLM returns **structured
   analysis**: drivers, prediction/score, coverage, **prioritized recommendations**, drill-down
   suggestions, chart spec (LLM call 2).
4. Browser renders. Follow-ups repeat the loop, scoped to the previous cohort.

### Why this approach (vs the alternatives)
- **vs. keep-everything-client-side (today):** moving the LLM calls to the server **removes the API keys
  from the browser bundle** — the one real security hole left — and centralizes the "analyst brain"
  (playbooks, orchestration, recommendation logic) so it's auditable and swappable.
- **vs. full server-side DuckDB:** the free Render tier (512 MB RAM) can't comfortably hold the 190 MB
  Preview dataset **plus** Node. Keeping SQL execution in the browser avoids that entirely and reuses the
  engine that already works. The server stays **light** (LLM calls only — no DuckDB, no big memory).
- **Fits what we already have:** `server.mjs` is already deployed on Render behind auth; we just add
  `/api` routes to it. No new service.

### Migration safety
- The **current chat stays working** during the build. The new analysis features use the `/api` path from
  the start (new = no breakage).
- **Optional follow-up security upgrade:** route the existing chat's LLM call through `/api/plan` too, so
  keys leave the browser everywhere. Do this as a separate, clearly-scoped change.

## 2. The three layers

1. **Data layer (truth):** rule-based SQL views in DuckDB (`v_dropout_risk`, `v_center_health`, …).
   Every number is computed here — reproducible, grounded. **No ML.**
2. **Brain layer (server orchestration):** the `/api` pipeline that turns a request into SQL, runs the
   interpretation, and produces predictions + recommendations. Uses the LLM for language + query-writing,
   never for inventing numbers.
3. **Knowledge layer (in-context, NOT trained):** **analysis playbooks** — per analysis, a small spec the
   server injects into the prompt. This is how the LLM "knows" each analysis without any training/ML.

### Playbook shape (per analysis)
```
id, title
factors:        which columns + weights make the score
interpret:      thresholds ("70+ = urgent"), what the number means
coverage_rule:  which fields drive confidence; how to report gaps
diagnose:       how to find the top driver(s)
prioritize:     ranking rule (severity × #students × coverage)
actions:        driver → suggested action (advisory)
escalation:     contact if available, else "report to field officer"
drilldowns:     2–3 sensible next questions
mode_notes:     Real behavior vs Preview behavior
```

## 3. Data plan

### Real views (additive to `semantic.sql`, documented in `catalog.ts`, guarded by `check:catalog`)
`v_coverage` (foundation), `v_dropout_risk`, `v_irregular_escalation`, `v_center_health`,
`v_center_performance`, `v_weakest_subjects`, `v_economic_pressure`, `v_vulnerability`, `v_ghost_students`,
`v_overage_grade`.

### Preview extensions (generated by `build-tuned-data.mjs`, following the `attendance_monthly` pattern:
present in Preview, empty/stub in Real, watermarked, real-mode-graceful)
1. **Dated attendance** (monthly, per student/center) → enables **1-month / 6-month toggles**.
2. **Center performance monthly series** → center trends over time.
3. **Teacher ↔ center ↔ batch ↔ subject assignment** → enables the teacher drill-down (real data links
   teachers to Center ID only; Preview simulates the batch/subject link).
4. **Contact / field-officer reference** → enables "who to contact / report to."

> Rule: simulate **only** what was never collected; keep it realistic; never present it as real.

---

## 4. Relational drill-down

Each follow-up is a SQL query scoped to the previous cohort, joined on the keys that exist
(student ↔ center ↔ attendance ↔ assessment ↔ profile) and — in **Preview** — the simulated links
(teacher ↔ batch ↔ subject, contact). Example chain (worst centers):
worst centers → **why** (5 ME category breakdown) → attendance → worst-attendance students → their income
→ weakest subjects → **(Preview)** the batch's teacher → prioritized action items.
**Discipline:** show data coverage at **every hop** (sparsity compounds).

---

## 5. Decision / recommendation layer (KEY)

Every analysis ends with, not a bare number:
- **Prioritize** — rank issues by severity × #students affected × data coverage ("fix Center X first").
- **Diagnose** — the top driver(s) behind the score/issue.
- **Recommend** — advisory action(s) from the playbook (weak Pedagogy → teacher coaching; low income →
  cash support; low attendance coverage → fix reporting).
- **Escalate/contact** — real contact if the reference has one; otherwise "report to the field officer."
- All **advisory + explainable + coverage-aware** — the human decides.

## 6. Real vs Preview behavior

| | Real mode | Preview mode |
|---|---|---|
| Scores | honest + coverage badge (some thin) | fuller, watermarked "estimated" |
| Time toggles (1/6 mo) | **not available** — use cycle / programme / enrollment period | **available** (simulated dated data) |
| Teacher drill-down | "teachers at this center" only | full teacher ↔ batch ↔ subject |
| Contacts | field-officer / generic | simulated contact if in reference |

Same views serve both; the toggle swaps the data; only labels/watermarks differ.

### Mode-based visibility (what shows in each mode)

Each analysis **card** and each drill-down **chip** declares the data it needs, and the UI is **filtered by
the active mode** — so users never see something the current DB can't answer:

- **Real mode** → shows ONLY analyses the real data supports (dropout risk, irregular→dropout, center
  health, worst centers, economic pressure, weakest subjects, vulnerability, ghost/over-age). Preview-only
  analyses and drill-downs (month/6-month trends, teacher↔subject, contacts) **do NOT appear at all.**
- **Preview mode** → shows EVERYTHING, including the simulated-data analyses — all watermarked
  "estimated — demonstration only."

So the analysis set **grows** when you switch to Preview and **shrinks back to the honest subset** in Real.
Analyses that work in both simply show real-with-coverage in Real and fuller-watermarked in Preview.

> *Optional (your call):* instead of fully hiding preview-only cards in Real, show them **greyed/disabled**
> with a hint "Available in Preview — needs dated data." This doubles as the data-collection pitch
> ("collect X and this unlocks for real"). Default is to hide; say the word to grey-out instead.

## 7. Phased build order

- **Phase 0 — Foundation:** add `/api/plan` + `/api/analyze` to `server.mjs` (keys server-side);
  `v_coverage` layer; one analysis (**Dropout risk**) end-to-end (server brain → browser SQL → render);
  validate vs the 5,332 real dropouts.
- **Phase 1 — Tier 1:** dropout risk, irregular→dropout, center data-trust, vulnerability stacking +
  their playbooks + drill-down chips + welcome-screen cards.
- **Phase 2 — Tier 2 + decision layer:** worst-performing centers, economic-pressure, weakest subjects;
  build out prioritize / diagnose / recommend / escalate.
- **Phase 3 — Preview extensions + Tier 3:** dated attendance, center monthly, teacher-batch, contacts →
  month toggles, teacher drill-down, attendance-trend forecasting demos.

Each phase is independent and additive.

## 8. What changes vs stays the same

**New (additive):** `/api` analysis routes on `server.mjs`; the analysis SQL views; the playbooks;
predictive cards on the welcome screen; drill-down suggestion chips; the Preview data extensions.
**Unchanged:** the current chat UX, the dashboards, the data flow, the auth/deploy model. (Optional later:
move the existing chat's keys behind `/api` too.)

---

## 9. Guardrails (unchanged, non-negotiable)

- Rule-based + explainable — **no ML / no trained model**. LLM writes SQL + reasons; numbers come from SQL.
- Every analysis states its **data coverage**; low coverage says so.
- Preview results **always** watermarked "estimated — not for decisions."
- Simulate only genuinely-uncollected data, **only in Preview**, clearly labeled.
- Recommendations are **advisory + explainable**; the human decides.
- **Additive only** — never change the existing chat/query flow.
- Any incoming plan is checked against the real code + Real/Preview reality **before** building.
- Work on a branch, locally; **no commit/push and no QA/e2e until "push to main."**
